# Step 0.2 - Body Lifecycle and Command Buffer

## Metadata

- Status: Implemented（2026-07-16）
- Priority: Core / Blocker
- Depends on: Step 0.1
- Estimate: 2-3 days

## Goal

建立确定的 Body 创建、更新、销毁和映射生命周期，消除 immediate create、延迟 destroy、组件重建之间的竞态与残留 Body。

## Implemented result

- `PhysicsCommandBuffer` 使用 command variant 统一 Create、Destroy、Rebuild、Teleport、KinematicTarget、Velocity、Force、Impulse，并提供容量、pending、peak、enqueue、reject 和 clear 统计。
- `PhysicsScene::PreStep` 对同 owner 的结构命令执行 last-intent coalescing，再固定按 `Destroy -> Create/Rebuild -> Transform -> Velocity/Force` 提交；同 phase 保持 enqueue sequence。
- `PhysicsBodyRegistry` 由 Scene 持有 engine handle，记录 opaque backend token、owner GameObjectID、Collider Handle 占位、MotionType 和 active state，并维护 owner -> handle 索引。
- Jolt `BodyID` 现在只包装为 `PhysicsBackendBodyToken` 穿过 adapter 边界；engine handle generation 由 Scene registry 分配，Jolt user data 仍只保存 engine handle。
- Rebuild 先创建新 backend Body；创建失败保留旧 Body，成功后 retire 旧 token 并原子替换 owner 映射。同 owner Create 会返回 `DuplicateOwner`。
- Runtime gameplay 已从 immediate create 迁移到 queue；`CreateBodyImmediate` 只保留给初始化和测试，并在公共 API 标记受限。
- Rigidbody 在 `Start`、Play/Paused 状态的 Enable/Dirty/Disable/Destroy 中只提交 owner-targeted command；同一 fixed step 的 create/disable/enable 会保留最终意图。
- Scene StartPlay、StopPlay、Subsystem Cleanup 和重复 Reset 都会清理 Body、backend token、pending command、raw contact queue 和 transform snapshot。

## Remaining risks

- owner-targeted movement command 会在执行阶段解析当前 Body，适合“同一 PreStep 先 Create/Rebuild 再施力”；handle-targeted command 不会 fallback 到 replacement，避免旧 Handle 意外控制新 Body。
- command queue 默认容量为 4096；溢出返回 `QueueFull` 并进入统计，不会静默扩容。超出容量的业务突发需要项目配置或上层节流。
- velocity、impulse 和 Jolt kinematic move 按 Jolt 语义会唤醒 Body；Force/Teleport 额外支持 `KeepState/Wake/DoNotWake`。
- 销毁 Body 对未来 active contact pair 的分类与 Exit 生成仍由 Step 1.1 处理；本步骤只保证 backend raw event queue 在 Reset 时清空。

## Boundaries

- 本步骤不决定 Collider/Rigidbody 的最终 Inspector 结构。
- 不实现跨帧异步 physics world。
- 不实现 Collision/Trigger Enter、Stay、Exit 或 gameplay 广播。
