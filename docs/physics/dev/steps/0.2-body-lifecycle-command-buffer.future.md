# Step 0.2 - Body Lifecycle and Command Buffer

## Metadata

- Status: Planned
- Priority: Core / Blocker
- Depends on: Step 0.1
- Estimate: 2-3 days

## Goal

建立确定的 Body 创建、更新、销毁和映射生命周期，消除 immediate create、延迟 destroy、组件重建之间的竞态与残留 Body。

## Current problem

- `CreateBodyImmediate` 与 destroy queue 使用不同提交时机。
- destroy 只执行 Jolt `RemoveBody`，完整销毁与 registry 清理语义没有测试。
- `Rigidbody::OnDirty` 会先排队销毁旧 Body，再立即创建新 Body，同一 owner 可短暂存在多个映射。
- PhysicsScene 使用 raw handle -> GameObjectID 单向映射，无法高效拒绝同 owner 重复注册。
- 命令向量没有统一顺序、错误返回、wake policy 或 stale handle 统计。

## Planned modules

- `PhysicsScene`
- `IPhysicsBackend` / `PhysicsJoltBackend`
- new `PhysicsCommandBuffer`
- new `PhysicsBodyRegistry`
- `PhysicsSubsystem`
- `Rigidbody` lifecycle integration
- `tests/integration/PhysicsLifecycleTests.cpp`

## Implementation checklist

- [ ] 定义 Create、Destroy、Rebuild、Teleport、KinematicTarget、Velocity、Force、Impulse 的 command variant。
- [ ] 所有结构变更在 `PreStep` 提交；公开 immediate API 仅限初始化/测试并标记受限。
- [ ] Registry 保存 engine handle、backend body token、owner GameObjectID、ColliderID、motion type 和 active state。
- [ ] 创建失败不注册 handle；重建采用 create-new 成功后再 retire-old，失败时保留旧 Body 或明确禁用。
- [ ] destroy 执行 remove + destroy，释放 backend slot，并在 generation 增长后回收 engine index。
- [ ] owner destroy/disable、Scene StopPlay 和 subsystem Cleanup 都能幂等清空 command/contact/body state。
- [ ] 命令按 `Destroy -> Create/Rebuild -> Transform -> Velocity/Force` 的固定规则处理，并拒绝 stale handle。
- [ ] 为队列容量、失败命令、active bodies 和 stale commands 增加统计。

## Acceptance criteria

- 连续启用/禁用或修改 Rigidbody 1000 次后，PhysicsScene 和 Jolt active/body 数与最终组件状态一致。
- 同一 GameObject 的单 Body MVP 不会出现重复注册。
- Destroy 后旧 handle 的速度、冲量和 transform 命令被安全拒绝。
- Scene 退出 Play 后没有残留 Body、pending command 或 contact pair。
- 命令处理顺序在相同输入下稳定。

## Risks

- 组件 Awake/Enable/Dirty/Destroy 可能在同一帧组合发生，command coalescing 必须保留最终意图。
- 销毁 Body 会影响 active contact pair，必须为 Step 1.1 保留 pair cleanup hook。

## Boundaries

- 本步骤不决定 Collider/Rigidbody 的最终 Inspector 结构。
- 不实现跨帧异步 physics world。
