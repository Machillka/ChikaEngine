# Step 6.1A - HDR/EXR Floating-Point Texture Contract

## Metadata

- Status: Implemented (2026-07-15; Step 6.2A integration validation complete)
- Depends on: Step 6.1
- Unblocks: Step 6.2A and Step 6.3
- Estimate: 3-5 days

## Goal

让 Radiance `.hdr` 与 OpenEXR `.exr` 在 Asset -> Resource -> RHI 上传链中保留线性浮点值，包括大于 `1.0` 的亮度；本卡只建立格式正确的解码和上传契约，不负责把等距柱状图转换为 Cubemap，也不修改 Skybox Pass。

## Implemented Contract

Step 6.1A 已贯通 HDR/EXR 的保真解码和上传契约：

- PNG/JPEG/TGA 等 LDR 图片继续通过 `stbi_load(..., 4)` 解码为 `UNorm8`，保持原有路径。
- Radiance `.hdr` 使用 `stbi_loadf(..., 4)`；OpenEXR 使用 TinyEXR v3，统一输出 linear RGBA。
- `TextureData` 保存 `TexturePixelStorage`、`TextureSourceEncoding`、`rowBytes` 与 `layerBytes`，payload 不依赖 RHI/Vulkan 类型。
- `format=auto|rgba16f|rgba32f` 控制浮点 payload；HDR/EXR 的 `auto` 为 Float16，显式诊断路径可选择 Float32。
- ResourceManager 根据 storage 映射 `RGBA8_*`、`RGBA16_Float`、`RGBA32_Float`，并在创建 GPU 资源前校验 tight row/layer/total byte layout。
- Asset、Resource 和 Environment status 已区分 decode failure、unsupported EXR、invalid float payload 与 GPU upload failure。

自动测试使用运行时生成的小型 HDR/EXR fixture，验证大于 `1.0` 的值进入 staging payload；单张 equirectangular 转 Cubemap 与实际 Skybox 采样已由 Step 6.2A 完成。

## Decisions

### Decoder boundary

- Radiance `.hdr` 使用现有 `stb_image` 的 `stbi_is_hdr` / `stbi_loadf(..., 4)`，解码结果为线性 RGBA32 float。
- OpenEXR 使用 TinyEXR，并建立正式、可审计的 CMake target 和 license 记录。
- 仓库目前只有 `engine/ThirdParty/tinygltf/examples/common/tinyexr.h`；实现时不得直接 include `tinygltf/examples`。应把 TinyEXR 作为引擎明确拥有的 pinned dependency 接入，避免示例目录升级或裁剪时破坏 Asset 模块。
- 首版 EXR 支持普通 2D scanline/tiled RGB(A) 图像；deep、multipart、volume EXR 不在范围内，并返回包含文件路径与不支持特性的诊断。

### Asset contract

- 在 Asset 层增加后端无关的像素存储语义，例如 `UNorm8`、`Float16`、`Float32`；Asset 类型不得直接保存 `VkFormat` 或依赖 RHI 头文件。
- `TextureData` 的 payload 必须能表达任意 texel byte size，并提供可验证的 `rowBytes`、`layerBytes`、总字节数或等价信息。
- HDR/EXR 解码结果始终是 linear；浮点纹理配置 `srgb=true` 必须拒绝并输出明确错误，不能静默改写。
- 解码阶段不执行 exposure、tone mapping、gamma 或 clamp-to-1；这些操作属于 Skybox intensity 和 Post Process。
- 默认 GPU 存储为 `RGBA16_Float`，兼顾动态范围与显存；descriptor 可显式请求 `RGBA32_Float` 作为精度诊断路径。

### Upload contract

- Resource 层把 Asset pixel storage 映射到 `RHI_Format`，并按格式计算 staging byte size，禁止继续假设每像素固定 4 bytes。
- `TextureUploadRequest.format`、TextureDesc、TextureGPU.format 与实际 payload 必须一致。
- `CopyBufferToTexture` 的 mip/layer layout 必须由显式 upload region 或经过验证的紧密布局描述；本卡至少覆盖 mip 0 和全部 array layers。
- `EnvironmentResourceResolver` 继续只验证 TextureCube/view/sampler 契约，不按 `RGBA8` 写死格式。

## Descriptor Contract

六面浮点 Cubemap 可以沿用 `.texture` 描述文件：

```json
{
  "usage": "environment",
  "format": "rgba16f",
  "srgb": false,
  "generateMips": false,
  "mipLevels": 1,
  "cubeFaces": {
    "px": "right.exr",
    "nx": "left.exr",
    "py": "top.exr",
    "ny": "bottom.exr",
    "pz": "front.exr",
    "nz": "back.exr"
  }
}
```

Rules:

- `format`: `auto | rgba16f | rgba32f`；HDR/EXR 的 `auto` 选择 `rgba16f`。
- 六个 face 必须具有相同尺寸、通道语义和浮点存储类型；首版不允许同一个 Cubemap 混用 LDR、HDR 和 EXR。
- 浮点环境资源必须显式或推导为 `srgb=false`。
- `generateMips=true` 只有在实现真实 mip 生成后才可接受；不能继续出现“标记为 true 但只上传 mip 0”的静默行为。
