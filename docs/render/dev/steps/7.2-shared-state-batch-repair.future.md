# Step 7.2 - Shared-state Batch Repair

## Metadata

- Status: Implemented (2026-07-03)
- Depends on: Step 3.5 render sort/batch builder, Step 4.8 GPU-driven correctness gate, Step 7.1 material runtime resource API
- Area: Renderer/RenderQueue/RenderPipeline/RenderSubsystem
- Estimate: 2-3 days

## Goal

修复 Renderer 对多个共享渲染状态的 GameObject 仍然按对象级别提交 Draw 的问题。

完成后，同一 Pass 中共享 `Pipeline + Material resource + Mesh resource` 的静态对象必须合并为一个 `RenderBatch`，CPU 路径通过一次 `DrawIndexed(..., instanceCount=N, firstInstance=...)` 提交，GPU-driven 路径通过一个 draw group / indirect command 提交。

本步骤只修复 batch/instancing 提交语义，不改变材质编辑、Asset 持久化、透明排序或蒙皮渲染策略。

## Current Context

- `RenderPacket` 已保存 `pass`、`pipeline`、`material`、`mesh`、`object` 和 `instancingEligible`。
- `RenderBatch` 已保存 `pipeline`、`material`、`mesh`、`firstPacket`、`packetCount`、`firstInstance` 和 `instanced`。
- `RenderQueue.cpp` 的 `BuildBatchesInternal()` 已尝试把连续且共享 `pipeline/material/mesh/pass` 的 instancing eligible packet 合并。
- `RenderPipeline::PrepareInstanceData()` 会为 instanced batch 写入连续 instance matrix，并回填 `RenderBatch::firstInstance`。
- `RenderPipeline::DrawRenderQueue()` 对 instanced batch 调用 `DrawIndexed(mesh.indexCount, batch.packetCount, ..., batch.firstInstance)`。
- 原始问题表现为每个 GameObject 单独创建 Draw，说明 batch 合并契约此前没有被稳定验证，或者某一层破坏了共享状态身份。

## Suspected Failure Points

优先按下面顺序排查，不直接假设只有一个原因：

- Resource identity 不共享：相同 material/mesh path 在 Asset/Resource 层被解析成不同 handle，导致 sort key 不同。
- Packet eligibility 被意外关闭：对象被标记为 `Skinned`、`Transparent` 或进入非静态路径，导致 `instancingEligible=false`。
- Batch 构建时机不对：parallel packet append 后未对最终合并队列执行 sort + build，或 stale batches 未清空。
- CPU instance data 未与 batch 对齐：`firstInstance`、`packetCount`、instance buffer 写入顺序与 Draw 使用顺序不一致。
- Draw 统计误读：`instanceCount=N` 的一次 instanced Draw 被统计或展示成 N 个对象，需要区分 `drawCallCount` 和 `instanceCount`。
- GPU-driven residual path 与 CPU batch path 混用：static opaque 被 GPU path 消费后，CPU residual path 不应重复逐对象提交。

## Responsibility

- `RenderSubsystem` 保证相同 asset handle 复用同一 Resource handle，不在每个 GameObject 上创建独立 GPU Material/Mesh。
- `RenderQueue` 定义 batch key 和可实例化条件，只负责 packet 排序与 batch 构建。
- `RenderPipeline` 负责把 batch 转换成 instance buffer 和实际 Draw 命令。
- `RenderDiagnostics`/tests 负责证明 draw call 数、batch 数和 instance 数符合预期。
- Transparent、Skinned、per-object override 和 MaterialInstance 不在本步骤内合并。

## Proposed Contract

### Batch Key

Opaque/static batch 的最小合并 key：

```cpp
struct BatchKey
{
    RenderPassClass pass;
    PipelineHandle pipeline;
    Resource::MaterialHandle material;
    Resource::MeshHandle mesh;
};
```

不应把 `GameObjectID`、world transform、object pointer、AABB 或 debug name 放入合并 key。对象身份只作为稳定排序 tie-breaker，不能阻止共享状态合并。

### Eligibility

允许合并：

- static opaque object
- shadow pass static caster
- GBuffer opaque static object
- same `Pipeline + Material + Mesh + Pass`

暂不合并：

- transparent object，仍保持远到近排序
- skinned object，骨骼 buffer 不同
- material instance/per-object override，后续需要独立 key
- texture slot runtime replacement 正在变更 descriptor 的对象

## Implementation Steps

1. 建立复现测试
   - 在 `tests/unit/RenderBaselineTests.cpp` 或新增 `tests/unit/RenderBatchSubmissionTests.cpp` 构造 10 个共享 mesh/material/pipeline 的静态对象。
   - 覆盖 Forward Opaque、GBuffer Opaque、Shadow 三类 pass。
   - 断言 `packets=10`、`batches=1`、`batch.packetCount=10`、`batch.instanced=true`。

2. 增加 Draw 提交级测试
   - 使用 mock `IRHICommandList` 记录 `DrawIndexed` 调用次数和 `instanceCount`。
   - 验证共享状态 batch 只提交 1 次 Draw，`instanceCount=10`。
   - 验证两个不同 material 或 mesh 会拆成 2 个 Draw。
   - 验证 transparent 仍按 2 个对象提交 2 个 batch，不破坏排序。

3. 锁定 Resource handle 复用
   - 检查 `AssetManager` path/guid cache 是否让相同 material/mesh 得到同一个 asset handle。
   - 检查 `ResourceManager::UploadMesh()` 和 `UploadMaterial()` 是否对同一 asset handle 返回同一 resource handle。
   - 为重复 asset path 增加单元测试，避免 RenderSubsystem 每个 GameObject 得到独立 material resource。

4. 修复 Batch Key 与 sort key
   - 保留 object handle 作为 `RenderOpaqueSortKey` 最后的 tie-breaker。
   - 确认 `BuildBatchesInternal()` 只用 `pass/pipeline/material/mesh/instancingEligible` 判断 batch 边界。
   - 如果现有逻辑中任何 per-object 字段参与 batch 边界，移出 batch key。

5. 修复 parallel path 的 batch 构建时机
   - `AppendRenderQueueSet()` 只拼接 packets，不生成 batches。
   - 所有 worker 合并完成后统一执行 sort + `BuildRenderBatches()`。
   - 增加 worker count 1/2/4/8 的 batch count/hash 等价测试。

6. 修复 instance buffer 对齐
   - `PrepareInstanceData()` 必须在 batch 构建完成后执行。
   - 每个 instanced batch 写入连续 transforms，并回填 `batch.firstInstance`。
   - Draw 使用 `batch.packetCount` 作为 `instanceCount`，使用 `batch.firstInstance` 作为 `firstInstance`。
   - 增加测试验证不同 batch 的 `firstInstance` 不重叠且覆盖所有 packet。

7. 修复 GPU-driven parity
   - `BuildGpuDrivenFrameData()` 的 draw group key 与 CPU `BatchKey` 保持一致。
   - 相同 static opaque group 生成 1 个 `GpuDrawGroup` 和 1 个 indirect command。
   - GPU path 启用时，CPU residual path 跳过已由 GPU-driven 消费的 instanced batch，避免重复提交。

8. 更新统计与调试
   - `RenderFrameStatistics` 中确认 `drawCallCount`、`instanceCount`、`packetCount`、`batchCount`、`instancedBatchCount` 含义。
   - 如果 UI/日志只显示对象数，补充显示 draw call 与 instanced batch，避免误读。
   - Benchmark JSON 中保留 batch 与 draw call 证据。

9. Editor/Benchmark smoke
   - 使用 `engine/editor/src/main.cpp` 中重复 Box/Floor material 的场景作为 smoke。
   - Forward mode：重复对象应表现为 batch 数明显小于 visible object 数。
   - Deferred mode：GBuffer pass 也应合并。
   - GPU mode：`dynamic-5k` 或 `instance-100k` 应显示 draw group / indirect command 明显小于 object count。

## Acceptance Criteria

- 同一 pass 中 10 个共享 mesh/material/pipeline 的 static opaque GameObject 只产生 1 个 instanced batch。
- CPU path 对该 batch 只录制 1 次 `DrawIndexed`，`instanceCount=10`。
- `batch.firstInstance` 指向 instance buffer 中该 batch 的连续矩阵范围。
- Forward Opaque、GBuffer Opaque 和 Shadow pass 都满足共享状态合并。
- Transparent 仍保持远到近排序，不为了合并破坏透明语义。
- Skinned 对象不会错误复用 static instance buffer。
- GPU-driven path 对同状态 static opaque 对象生成 1 个 draw group / indirect command。
- `drawCallCount`、`batchCount`、`instancedBatchCount` 能证明合并生效。

## Boundaries

- 不在本步骤实现 transparent instancing。
- 不在本步骤实现 skinned mesh instancing。
- 不在本步骤实现 per-object MaterialInstance。
- 不修改 material JSON 或材质参数编辑语义。
- 不为了减少 draw call 改变排序正确性或可见性结果。
- 不把 GPU-driven 结果当作 CPU batch 修复的替代品；两条路径都要有独立验证。

## Risks

- 统计误读会让问题看起来仍未修复：必须区分 object count、packet count、batch count、draw call count 和 instance count。
- 如果 Resource handle 不共享，RenderQueue 层再正确也无法合 batch。
- 如果未来 MaterialInstance 引入 per-object override，需要把 material instance handle 纳入 batch key，否则会把不同参数对象错误合并。
- Transparent 合并容易破坏排序，必须明确排除。

## Recommended Order

1. 先写 RenderQueue/Draw submission 复现测试，证明当前失败模式。
2. 再检查 Resource handle 复用，确认不是 asset/resource 身份导致 key 不同。
3. 修复 batch key、parallel sort/build 时机和 instance buffer 对齐。
4. 补 CPU path draw call 断言。
5. 补 GPU-driven draw group parity 断言。
6. 最后跑 Editor/Benchmark smoke 并记录统计证据。
